# UPC Fig. 4 불일치 제한 감사와 후속 프로토콜 결정

## 1. 결론

논문으로 정당화할 수 있는 10개 변형을 실행했지만 Fig. 4의 24개 그룹 수와 정확히
일치하는 절차는 찾지 못했다. 최선의 결과는 다음 조합이며 Fig. 4와의 L1 차이는
`4`다.

- 2013년 11월 1일을 제외한 11월 4~29일의 완전한 4주 평일 20일
- 한 시간의 10분 관측 6개를 합산
- 날짜별 peak의 최빈값이 아니라 시간별 평균 profile의 최대값
- 전처리에서 채운 0을 유지
- `float64` 또는 `float32` 계산

남은 차이는 hour 11에서 `-1`, hour 15에서 `+2`, hour 18에서 `-1`이다. 한 셀을
다른 그룹으로 옮기면 두 그룹의 오차가 각각 1씩 바뀌므로, 최소 두 셀의 membership이
논문 그림과 다르다는 뜻이다.

이 결과로 `GAP-UPC-06`의 원인을 확정할 수는 없다. 대신 공개 정보로 가능한 내부
감사는 완료됐으며 다음 결정을 고정한다.

| 역할 | 고정한 선택 |
|---|---|
| 주 성능 실험 | `train_only` |
| 논문 Algorithm 1 민감도 실험 | `algorithm1_full_month` |
| Fig. 4 원인 진단 | `figure4_probe_complete_weeks_sum_mean_profile_f64_zero` |
| 진단 membership의 모델 입력 사용 | 금지 |
| 독립 기준선 진행에 Fig. 4 정확 일치 필요 | 아니요 |
| “Fig. 4 정확 재현” 주장에 정확 일치 필요 | 예 |

따라서 Fig. 4 불일치는 독립 기준선과 PCC 구현을 막지 않는다. 다만 원저자의 추가
자료가 없으면 “Fig. 4를 정확히 재현했다”고 쓰면 안 된다.

## 2. 왜 제한 감사가 필요한가

그림의 숫자에 가까워질 때마다 기간, 결측값 또는 집계 규칙을 새로 바꾸면 결국 우연히
맞는 조합을 고를 수 있다. 그 조합은 논문의 실제 절차를 설명한다는 보장이 없고,
후속 모델 성능까지 보고 선택하면 평가 누수도 생긴다.

이를 막기 위해 실행 전에 다음 계약을 config에 기록했다.

1. 논문과 데이터 해상도 때문에 생기는 모호성만 변형으로 허용한다.
2. 선언한 10개 변형을 각각 한 번씩 실행한다.
3. 결과를 본 뒤 변형을 추가하지 않는다.
4. 정확 일치가 나와도 “저자가 그 절차를 사용했다”는 증거로 간주하지 않는다.
5. 정확 일치가 없어도 독립 기준선은 진행한다.

[`configs/upc_fig4_audit_milan_nov2013.json`](../configs/upc_fig4_audit_milan_nov2013.json)은
후보의 이름과 순서까지 고정한다. 후보를 임의로 추가하거나 순서를 바꾸면 프로그램이
실행을 거부한다.

## 3. 감사한 요인

### 3.1 날짜 범위

- `full_month`: 논문 Algorithm 1 해석에 따라 11월의 평일 21일 사용
- `complete_weeks`: 월요일부터 금요일까지 완성된 4주, 즉 11월 4~29일의 평일
  20일 사용

11월 1일은 금요일 한 날만 떨어져 있다. 이를 제외하는 선택은 달력상 가능한 구현
가설이지만 논문에 명시돼 있지 않으므로 진단에만 사용한다.

### 3.2 대표 peak 계산

- `daily_peak_mode`: 각 날짜의 peak hour를 구한 뒤 최빈값 선택. Algorithm 1에
  명시된 방식이다.
- `mean_hourly_profile`: 날짜별 시간 traffic을 먼저 평균한 뒤 가장 큰 hour 선택.
  Fig. 4에 가까워지지만 논문에 명시되지 않은 방식이다.

### 3.3 10분 관측의 시간 집계

- `sum`: 한 시간의 10분 관측 6개를 합산
- `max`: 6개 중 최대값 사용

정상적인 hour에는 항상 6개 관측이 있으므로 `sum`과 `mean`은 양의 상수배 관계다.
따라서 argmax가 같아 `mean`을 별도 변형으로 중복 실행하지 않았다.

### 3.4 부동소수점과 결측

- `float64`와 `float32`로 동일한 최선 후보를 각각 실행
- 전처리의 0을 그대로 사용하는 정책과, 결측 또는 Internet-all-null 표시가 있는
  10분값을 제외하고 남은 값으로 한 시간을 재정규화하는 정책 비교

결측 제외는 결과를 유리하게 만들기 위한 임의 삭제가 아니라, 공개되지 않은 결측
처리의 영향을 한 번 확인하는 민감도 검사다.

## 4. 실제 결과

|---|---:|---|---|---|---:|---:|
| Algorithm 1 전체 월 | 21 | 합계 | 일별 peak 최빈값 | f64·0 유지 | 3/24 | 1,180 |
| 전체 월 평균 profile | 21 | 합계 | 평균 profile peak | f64·0 유지 | 7/24 | 340 |

| **완전한 4주 Fig. 4 probe** | **20** | **합계** | **평균 profile peak** | **f64·0 유지** | **21/24** | **4** |

결과가 말해 주는 범위는 명확하다.

- `float32`와 `float64`의 membership은 10,000셀 모두 같아 남은 차이의 설명이 아니다.
- 결측 제외 정책은 단 한 셀의 membership만 바꾸며 L1을 `4`에서 `6`으로 늘린다.
- 시간별 최대값은 모든 조합에서 크게 나빠져 합계 대신 사용했다는 설명을 지지하지
  않는다.
- 완전한 4주와 평균 profile을 함께 사용해야 Fig. 4에 매우 가까워진다.
- 그러나 “가깝다”는 사실만으로 미공개 절차를 저자의 절차라고 확정할 수 없다.

전체 24개 그룹 수, 시간대별 차이, membership SHA-256과 변형 간 membership 차이는
`data/processed/upc/audits/fig4_audit.json`에 기록된다. 데이터 산출물이므로 Git에는
포함하지 않는다.

## 5. 실행 방법

선행 UPC 입력 검증과 초기 그룹 생성을 실행한다.

```bash
.venv/bin/python -m scripts.build_upc_initial_groups \
  --config configs/upc_milan_nov2013.json
```

현재 config는 Fig. 4 불일치를 알고도 독립 실험을 진행하기로 결정했으므로 이 명령은
종료 코드 `0`을 반환한다. `data/processed/upc/manifest.json`의 상태는 계속
`diagnostic_mismatch`이며 불일치 자체를 숨기지 않는다.

제한 감사를 실행한다.

```bash
.venv/bin/python -m scripts.audit_upc_fig4 \
  --config configs/upc_fig4_audit_milan_nov2013.json
```

실제 노트북의 WSL 실행에서 10개 변형 전체는 약 `4.5초`, 최대 RSS는 약 `311MiB`,
swap은 `0`이었다. memory map과 셀 chunk `256`을 사용하므로 32GB RAM 중 Codex와
다른 앱이 절반가량을 쓰는 상황도 충분히 감당한다. GPU 이점이 없어 이 감사에는
Colab을 사용하지 않는다.

## 6. 산출물과 결정성

| 파일 | 내용 | 크기 | SHA-256 |
|---|---|---:|---|
| `fig4_audit.json` | 모든 변형의 그룹 수·차이·membership hash | 28,628 bytes | `2ce12e572cd18f1ed4418ce655e3a0118ac5fdf1c7b2ea53bf85cab16aaa5f87` |
| `fig4_audit_comparison.csv` | 변형별 핵심 비교표 | 3,100 bytes | `d43eb2cf45bdd760306e74a95c8d8ce8ce038ac6a2afef3d394b43f76a7510dc` |
| `fig4_audit_manifest.json` | 입력·config·환경·실행시간·출력 checksum | 실행별 metadata 포함 | 실행마다 생성 |

감사 도구는 진단 membership 배열을 파일로 내보내지 않는다. 보고서에는 비교를 위한
hash와 그룹 수만 남겨 후속 모델이 probe membership을 실수로 읽을 가능성을 줄였다.
합성 테스트는 다음을 검증한다.

- 일별 peak 최빈값과 평균 profile peak의 차이
- 시간 합계와 시간 최대값의 차이
- 결측 제외·재정규화 정책의 효과
- 감사 구현의 Algorithm 1 경로가 주 구현과 동일함
- 사전 등록되지 않은 후보 추가 차단
- 반복 실행한 JSON과 CSV checksum의 일치

## 7. 남은 외부 질문과 중단선

내부 후보 탐색은 여기서 중단한다. 다음 질문에 대한 원저자의 답변이나 생성 코드가
새로 확보될 때만 `GAP-UPC-06`을 다시 연다.

1. 2013년 11월 1일을 제외하고 완전한 4주만 사용했는가?
2. 일별 peak 최빈값 대신 평균 시간 profile의 peak를 사용했는가?
3. 10분 관측 6개를 한 시간으로 정확히 어떻게 집계했는가?
4. 결측과 국가코드별 Internet 공란을 어떻게 처리했는가?
5. Fig. 4 생성 코드나 10,000셀 UPC membership을 공유할 수 있는가?

외부 답변을 기다리는 동안 `train_only` 독립 기준선을 구현했고, 이어서 PCC와
`N=2` 군집화를 수행했다. `algorithm1_full_month`는 민감도 비교에만 사용했으며
Fig. 4 probe는 입력과 성능표에서 제외했다. 구현 결과와 새로 드러난 순서 민감도는
[UPC PCC 기반 최종 2개 클러스터](09-upc-pcc-final-clusters.md)에 기록했다.
