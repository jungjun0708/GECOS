# UPC 24개 초기 그룹 생성과 논문 지문 검증

## 1. 목적

이 단계는 GECOS의 전체 군집화나 RCTL 학습을 시작하기 전에, 각 셀을 대표 peak
hour `0~23`에 배정하는 UPC Algorithm 1의 첫 단계를 재현한다. 단순히 코드가
실행되는지만 확인하지 않고 논문 Fig. 4가 공개한 10,000셀 그룹 수를 재현 지문으로
사용해 시간대, 기간 선택, 집계 방식과 정보 누수를 검증한다.

실제 검증에서는 논문의 서술형 알고리즘과 Fig. 4가 서로 다른 계산을 암시하는 중요한
차이를 발견했다. 이 문서는 차이를 숨기거나 결과에 맞춰 알고리즘을 바꾸지 않고,
명시된 알고리즘과 그림에 가까운 진단 가설을 분리해 기록한다.

## 2. 입력과 선행 조건

실행 전에 다음 파일이 있어야 한다.

| 입력 | 역할 |
|---|---|
| `data/processed/manifest.json` | 전체 전처리 계약과 SHA-256 |
| `data/processed/traffic.npy` | `(10000, 4320)` Internet traffic, float32 |
| `data/processed/cell_ids.npy` | traffic 행에 대응하는 cell ID |
| `data/processed/timestamps_ms.npy` | 10분 간격 epoch millisecond 시간축 |
| `data/processed/missing_mask.npy` | 원본 행이 없는 셀-시점 표시 |
| `data/processed/internet_null_mask.npy` | Internet 값이 모두 공란인 셀-시점 표시 |
| `data/processed/central_900_manifest.json` | 중앙 900셀 선택 계약과 SHA-256 |
| `data/processed/central_900.csv` | 중앙 900셀 ID와 Grid 위치 |

프로그램은 두 manifest의 파일 크기와 SHA-256을 실제 입력과 다시 비교한다. 입력이
조금이라도 바뀌었거나 중앙 900셀 ID 순서가 달라지면 결과를 생성하지 않는다.

설정은 [`configs/upc_milan_nov2013.json`](../configs/upc_milan_nov2013.json)에
고정한다.

## 3. 논문에 명시된 Algorithm 1 구현

### 3.1 시간축과 1시간 traffic

1. epoch millisecond를 `Europe/Rome`으로 변환한다.
2. 모든 날짜가 local hour `0~23`과 minute `0, 10, 20, 30, 40, 50`을 갖는지
   확인한다.
3. 같은 local hour의 10분 traffic 6개를 합산한다.
4. 현지 시각 기준 월요일부터 금요일만 사용한다.

2013년 11월은 로마의 일광절약시간 종료 이후이므로 모든 관측 시각의 offset은
`+01:00`이다. 그래도 UTC에 1시간을 직접 더하지 않고 IANA timezone을 사용한다.

### 3.2 셀별 scaling과 대표 peak hour

각 프로토콜이 허용한 평일 안에서 셀별 min-max scaler를 독립적으로 적합한다. 그 뒤
다음 순서로 대표 peak를 정한다.

1. 셀과 날짜마다 24개 시간 합계 중 최대인 hour를 선택한다.
2. 한 날짜에서 최대값이 동률이면 가장 이른 hour를 선택한다.
3. 날짜별 peak hour의 빈도를 센다.
4. 가장 자주 등장한 hour를 셀의 대표 peak로 선택한다.
5. 최빈값이 동률이면 가장 이른 hour를 선택한다.

min-max scaling은 한 셀 안의 모든 값에 같은 양의 선형 변환을 적용하므로, 상수 셀이
아닌 경우 peak 위치가 바뀌지 않아야 한다. 구현은 scaling 전후의 일별 peak를 모두
계산해 실제로 같은지 검사했다. 두 프로토콜 모두 불일치한 cell-day는 `0`이었다.

## 4. 세 가지 실행 경로를 분리한 이유

| 이름 | 기간과 평일 수 | 대표 peak 계산 | 용도 |
|---|---:|---|---|
| `paper_faithful` | 11월 1~30일의 평일 21일 | 일별 peak의 최빈값 | 논문 본문과 Algorithm 1을 그대로 검증 |
| `train_only` | 첫 20 calendar day 안의 평일 14일 | 일별 peak의 최빈값 | 미래 정보 누수가 없는 후속 학습용 주 프로토콜 |
| `figure4_complete_weeks_mean_profile` | 11월 4~29일의 완전한 4주 평일 20일 | 시간별 평균 profile의 최대값 | Fig. 4 불일치 원인만 조사하는 진단 가설 |

세 번째 경로는 논문 Algorithm 1이 아니다. 공개된 Fig. 4와 매우 가까워지는 미공개
가설을 재현성 분석용으로 보존한 것이며, 주 결과나 `train_only`를 대체하지 않는다.

## 5. 실행 방법과 종료 코드

Python 3.12 환경에서 필요한 버전을 설치한다.

```bash
python3 -m pip --python .venv/bin/python install --requirement requirements/upc.txt
```

합성 데이터 테스트를 포함한 전체 테스트를 실행한다.

```bash
.venv/bin/python -m unittest discover -s tests -v
```

실제 데이터 결과를 생성한다.

```bash
.venv/bin/python -m scripts.build_upc_initial_groups \
  --config configs/upc_milan_nov2013.json
```

종료 코드의 의미는 다음과 같다.

| 코드 | 의미 |
|---:|---|
| `0` | 입력 검증과 논문 지문의 정확한 일치까지 완료 |
| `1` | config, 시간축, shape, checksum 또는 알고리즘 계약 오류 |
| `2` | 파일 시스템 오류 |
| `3` | 산출물과 진단 manifest는 생성했지만 논문 지문이 정확히 일치하지 않음 |

현재 실제 데이터 실행은 의도적으로 종료 코드 `3`을 반환한다. CI나 shell에서 이를
성공으로 바꾸지 않는다. `data/processed/upc/manifest.json`의 상태도
`diagnostic_mismatch`로 기록된다.

## 7. 불일치 원인 점검

계획에서 정한 순서로 확인한 결과는 다음과 같다.

1. **Timezone:** 첫 local 시각은 `2013-11-01 00:00:00+01:00`, 마지막은
   `2013-11-30 23:50:00+01:00`이며 30일 모두 24시간을 갖는다.
2. **10분→시간 집계:** 각 hour에 10분 값 6개가 정확히 들어가는 테스트를 통과했다.
   합계와 평균은 argmax 위치가 같지만, 일별 peak의 최빈값 대신 여러 날짜의 평균
   profile을 사용하면 Fig. 4에 급격히 가까워진다.
3. **Scaling:** scaling 전후 peak 불일치는 두 주 프로토콜과 진단 경로 모두 `0`이다.
4. **결측:** `paper_faithful`의 30,240,000개 선택 관측 중 완전 누락은 `1,850개`
   (`0.00612%`), Internet 전체 공란은 `2,873개`(`0.00950%`)다. 모두 전처리
   계약대로 0을 유지하고 별도 집계했다.

따라서 현재 가장 강한 설명은 다음 두 미공개 선택의 조합이다.

- 11월 1일 금요일을 제외하고 월요일에 시작하는 완전한 4주 사용
- 일별 peak의 최빈값이 아니라 평일 시간별 평균 profile의 peak 사용

그러나 남은 4개의 L1 차이는 공개 자료만으로 설명할 수 없다. 원저자 전처리 코드,
사용한 정확한 데이터 사본, 부동소수점 처리 또는 Fig. 4 label 생성 자료가 필요하다.
이 문제는 `GAP-UPC-06`으로 관리한다.

## 9. 자원 사용량과 Colab 역할

WSL 로컬 실제 데이터 실행 결과는 다음과 같다.

| 항목 | 측정값 |
|---|---:|
| wall time | 약 1.6~1.8초 |
| 최대 RSS | 약 307MiB |
| swap | 0 |
| cell chunk | 256개 |
| 계산용 chunk 추정치 | 약 12.4MiB |
| 실행 방식 | 단일 Python 프로세스, multiprocessing 미사용 |

`traffic.npy`와 두 mask는 memory map으로 읽고 256개 셀만 계산용 float64 배열로
변환한다. 노트북의 32GB RAM 중 Codex와 다른 앱이 상당 부분을 사용하는 상황에서도
여유가 충분하다. 이 단계는 GPU 이점이 없고 데이터 전송보다 로컬 실행이 빠르므로
Colab을 사용하지 않는다. Colab은 이후 LSTM/RCTL 학습에 사용한다.

## 10. 테스트가 보장하는 사항

신규 합성 테스트는 다음을 확인한다.

- `Europe/Rome` 변환과 UTC 날짜 경계
- 전체 21개 평일과 첫 20일 안의 14개 평일 선택
- 10분 값 6개의 1시간 합산
- 일별 최대값과 최빈값 동률에서 가장 이른 hour 선택
- 상수 셀 정책
- cell chunk 크기와 C/Fortran 메모리 배치에 대한 결정성
- Algorithm 1과 평균-profile 진단이 실제로 다른 방법임
- 입력 checksum 변조 차단
- 중앙 900셀 ID 매핑
- 반복 실행 산출물 checksum 일치

## 11. 여기서 얻는 학습과 다음 중단 조건

이번 단계의 핵심 학습은 “논문 의사코드를 구현했다”와 “논문 그림을 재현했다”가 같은
말이 아니라는 점이다. 정확한 공개 지문이 있었기 때문에 기간 선택과 집계 연산이라는
숨은 차이를 모델 학습 전에 발견할 수 있었다. 또한 `paper_faithful`과
`train_only`를 분리해 재현 충실도와 평가 누수 방지를 동시에 추적할 수 있게 됐다.

현재 다음 UPC 단계인 PCC 및 `N=2` 최종 군집화로 자동 진행하지 않는다. 먼저 다음
두 결과를 서로 다른 실험 변형으로 유지할지 결정하고, 어떤 결과도 Fig. 4와 정확히
일치한다고 주장하지 않아야 한다.

- 논문 서술을 따르는 `paper_faithful`
- 주 성능 평가에서 사용할 누수 방지 `train_only`

Fig. 4 진단 가설은 원인 조사와 비교에만 사용하며 모델 성능을 좋게 만들기 위한
사후 선택으로 사용하지 않는다.
